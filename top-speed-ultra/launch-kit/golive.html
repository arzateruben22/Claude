Ten steps to live payments. Stop at nine.

Steps 1 to 9 connect Supabase and Stripe in Stripe's test mode: real servers, real webhooks, no real money. Step 10 turns on live keys, and only when you decide. Nothing here is deployed yet.

  • $0a month on the free tiers
  • 2Edge Functions
  • 5tables with row-level security
  • ~$10a year for a domain (sign-in email)
Exit1

How it fits together

The game never sees a card and never sends a price. It sends your sign-in token and the item's id; the server charges what its own copy of the catalog says, and only Stripe's signed message can grant an item.

Keys, before you start

Two kinds of key. Mixing them up is the one mistake that can't be undone by a rebuild: if a secret leaks, roll it in the dashboard at once.

Public: goes in the game

  • The Supabase Project URL.
  • The anon or publishable key (sb_publishable_…). It's public by design: row-level security is what protects the data.

Secret: never in the game, chat, a screenshot or git

  • The service-role key or any sb_secret_… key.
  • The Stripe secret key (sk_test_…, later sk_live_…).
  • The webhook signing secret (whsec_…).
  • They live in Supabase's function secrets only. Claude never asks for them.

    migrations/0001_oc_ultra_store.sql · 6,559 bytes
    -- OC Ultra store: accounts, purchases, entitlements, the launch waitlist and invite codes.
-- Run once in the Supabase SQL editor (or `supabase db push`). Safe to read top to bottom: tables, then row-level
-- security, then grants. Nothing here holds card data: Stripe's hosted page takes the card and keeps it.
--
-- Who can do what (row-level security is on for every table):
--   profiles      a player reads, creates and updates only their own row (the 13+ answer; never a birth date)
--   purchases     a player reads only their own rows; only the service role (the stripe-webhook function) writes
--   entitlements  a player reads only their own rows; only the service role writes
--   waitlist      anyone may add an email (and a ZIP and who referred them); nobody but the service role reads
--   invite_codes  the service role only
-- The service role bypasses row-level security by design; its key lives only in the Edge Functions' secrets.

-- ------------------------------------------------------------------------------------------- tables
create table if not exists public.profiles (
  id           uuid primary key references auth.users (id) on delete cascade,
  display_name text check (display_name is null or char_length(display_name) between 1 and 24),
  is_13_plus   boolean not null default false,
  created_at   timestamptz not null default now()
);

create table if not exists public.purchases (
  id                     uuid primary key default gen_random_uuid(),
  user_id                uuid not null references auth.users (id) on delete cascade,
  sku                    text not null,
  stripe_session_id      text not null unique,          -- one row per Checkout Session: redelivered webhooks change nothing
  stripe_payment_intent  text,                          -- one-time payments: how a refund finds its purchase
  stripe_subscription_id text,                          -- the club: how a cancellation finds its purchase
  amount_cents           integer not null check (amount_cents >= 0),
  currency               text not null default 'usd',
  status                 text not null default 'paid' check (status in ('paid', 'refunded', 'ended')),
  roll_name              text check (roll_name is null or char_length(roll_name) between 1 and 24),  -- Founder Pack opt-in; the owner approves it
  created_at             timestamptz not null default now(),
  refunded_at            timestamptz
);
create index if not exists purchases_user_idx on public.purchases (user_id);
create index if not exists purchases_pi_idx on public.purchases (stripe_payment_intent) where stripe_payment_intent is not null;
create index if not exists purchases_sub_idx on public.purchases (stripe_subscription_id) where stripe_subscription_id is not null;

create table if not exists public.entitlements (
  user_id     uuid not null references auth.users (id) on delete cascade,
  entitlement text not null,                            -- an id from src/store/cosmetics.json
  sku         text not null,                            -- the purchase that granted it most recently
  granted_at  timestamptz not null default now(),
  revoked_at  timestamptz,                              -- set by a refund or the end of a subscription
  primary key (user_id, entitlement)
);

create table if not exists public.waitlist (
  email         text not null unique check (char_length(email) <= 254 and email ~* '^[^@\s]+@[^@\s]+\.[^@\s]{2,}$'),
  zip           text check (zip is null or zip ~ '^\d{5}$'),
  referral_code text not null unique default substr(md5(gen_random_uuid()::text), 1, 10),
  referred_by   text check (referred_by is null or referred_by ~ '^[0-9a-f]{10}$'),
  created_at    timestamptz not null default now()
);

create table if not exists public.invite_codes (
  code       text primary key check (code ~ '^[A-Z0-9-]{4,32}$'),
  max_uses   integer not null default 1 check (max_uses > 0),
  uses       integer not null default 0 check (uses >= 0 and uses <= max_uses),
  expires_at timestamptz
);

-- ------------------------------------------------------------------------------------------- row-level security
alter table public.profiles     enable row level security;
alter table public.purchases    enable row level security;
alter table public.entitlements enable row level security;
alter table public.waitlist     enable row level security;
alter table public.invite_codes enable row level security;

drop policy if exists "profiles: read own" on public.profiles;
create policy "profiles: read own" on public.profiles for select to authenticated using ((select auth.uid()) = id);
drop policy if exists "profiles: create own" on public.profiles;
create policy "profiles: create own" on public.profiles for insert to authenticated with check ((select auth.uid()) = id);
drop policy if exists "profiles: update own" on public.profiles;
create policy "profiles: update own" on public.profiles for update to authenticated using ((select auth.uid()) = id) with check ((select auth.uid()) = id);

drop policy if exists "purchases: read own" on public.purchases;
create policy "purchases: read own" on public.purchases for select to authenticated using ((select auth.uid()) = user_id);

drop policy if exists "entitlements: read own" on public.entitlements;
create policy "entitlements: read own" on public.entitlements for select to authenticated using ((select auth.uid()) = user_id);

drop policy if exists "waitlist: anyone may join" on public.waitlist;
create policy "waitlist: anyone may join" on public.waitlist for insert to anon, authenticated with check (true);

-- invite_codes: no policy at all, so only the service role reaches it

-- ------------------------------------------------------------------------------------------- grants
-- Belt and braces under the policies: the roles the page uses get only what they need, whatever the project's
-- default privileges are.
revoke all on public.profiles, public.purchases, public.entitlements, public.waitlist, public.invite_codes from anon, authenticated;
grant select, insert on public.profiles to authenticated;
grant update (id, display_name, is_13_plus) on public.profiles to authenticated;   -- an upsert sets every column it sends; the policy keeps id = you
grant select on public.purchases to authenticated;
grant select on public.entitlements to authenticated;
grant insert (email, zip, referred_by) on public.waitlist to anon, authenticated;
grant all on public.profiles, public.purchases, public.entitlements, public.waitlist, public.invite_codes to service_role;

    What live keys change

    With live keys, create-checkout sells only items whose every grant is marked ready in src/store/cosmetics.json. On 16 October 2026 none is: the paints wait for their render check, and the Founder badge, frame and roll are still to build. A live store shows each item as "On sale once it is in the game" until those statuses change, npm run store:sync runs and the functions are redeployed.

Keep Supabase awake

A free project pauses after a week with no activity, and a paused project can't answer Stripe's webhook. Stripe retries for up to three days in live mode; after that, resend the event from the dashboard. Check the project weekly, or run Pro ($25 a month) for the live months.

Switching the store off

Set VITE_PAYMENTS_LIVE=false (or delete the file), rebuild and deploy: the store goes back to test mode for everyone. Purchases stay in Supabase and Stripe; refund anyone affected from Stripe.

Exit4

What's checked, what's not

What the server refuses, what is still to build, and what nobody can check until the real services answer. Step 9 is the real test.

What each part refuses

  • create-checkout: no or expired sign-in (401); an unknown, unavailable or expired item, or with live keys one not yet in the game (409); a missing 18-or-guardian tick, or the club's renewal tick (400); a profile not marked 13+ (403); an item you already own all of (409). It never reads a price from the page.
  • stripe-webhook: any delivery whose signature doesn't match (HMAC-SHA256, 5-minute tolerance) gets a 400 and writes nothing. A redelivered event changes nothing. A refund takes back only what no other paid purchase of yours grants.
  • Row-level security: players read only their own purchases and entitlements; only the service role writes them. The waitlist takes anonymous sign-ups and shows them to nobody.

Not built yet

  • The club: the customer portal for cancelling online, the monthly paint handler, the consent record kept three years, and a lawyer's read of the renewal terms.
  • A refund-request button (until then the terms point to a support email, TODO).
  • The waitlist form and invite codes: the tables exist; nothing writes to them yet.
  • The Founders roll screen: names are stored on the purchase; the credits screen is still to build.
  • Disputes are ignored by design: no account is ever locked over one. Answer them in Stripe.

Verify at launch

  • Nothing has run in Supabase's Edge Runtime or against Stripe's API yet; the details come from documentation.
  • Supabase Auth's REST calls and the magic-link return; the Edge Runtime's JSON import and default secrets; --no-verify-jwt with the newer keys.
  • Stripe Checkout Sessions with price_data, the {CHECKOUT_SESSION_ID} placeholder, pay-what-you-want Prices, hosted pages on checkout.stripe.com (a custom checkout domain needs a one-line change in src/store/payments.ts).
  • That an unlisted redirect falls back to the Site URL (a third-party report).
